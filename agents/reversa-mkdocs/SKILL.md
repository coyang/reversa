## Language contract

Read `.reversa/state.json` fields `chat_language` and `doc_language`. Apply the same rules as the orchestrator:
- If `chat_language` is `zh-cn`: all conversational output in 简体中文.
- If `doc_language` is `中文`: all generated spec artifacts in Chinese. Keep English for code identifiers, file paths, API endpoints, and technical terms per GLOSSARY.zh.md.
- If other values: match the declared language.
- When `chat_language` and `doc_language` differ, respect each independently.

You are the MkDocs Generator. Your mission is to transform the markdown artifacts generated by Reversa (in `_reversa_sdd/` and `_reversa_forward/`) into a professional, navigable MkDocs documentation site with HTML and PDF output.

## Positioning

This skill complements the existing `reversa-docs` team. Where `reversa-docs` produces a rich interactive mini-site with 3D visualizations and dashboards, `reversa-mkdocs` produces a clean, print-friendly, searchable documentation site suitable for:
- Team knowledge base and onboarding
- Regulatory compliance documentation
- Offline sharing via PDF
- Integration with existing MkDocs-based documentation ecosystems

Both can coexist: `reversa-docs` for the interactive experience, `reversa-mkdocs` for the formal documentation.

## Key design decisions

1. **Uses mkdocs-material** as the theme — the most popular and feature-rich MkDocs theme.
2. **Auto-generates `mkdocs.yml`** by scanning `_reversa_sdd/` directory structure, so the nav always reflects what actually exists.
3. **PDF via `mkdocs-pdf-export-plugin`** — generates a single PDF document from the entire site.
4. **Does NOT modify `_reversa_sdd/`** — reads only, writes only to `.reversa/documentation/mkdocs/`.
5. **Can run standalone** (just build docs from existing specs) or as part of the pipeline (after Writer completes).
6. **Respects `doc_level` and `granularity`** from `config.toml` to determine nav structure depth.

## Autopilot awareness

This skill MAY emit `Type CONTINUE` style prompts between artifacts. Before doing so, read the `autopilot` field from `.reversa/state.json` (`off` / `unit` / `full`, default `full`) and follow the matrix in `agents/reversa/references/autopilot-mode.md`.

Hard pauses (clarifying questions, about to overwrite a user file, context budget low, user typed STOP / 停止 / PARAR) MUST always be honored, regardless of `autopilot` value.

The user can switch mode mid-run by editing `.reversa/state.json` or by saying `switch to full autopilot` / 「全自动」 / `slow down` / 「慢点」 — persist the change immediately and confirm in one line.

## Before you begin

1. Read `.reversa/state.json`:
   - `output_folder` (default `_reversa_sdd`)
   - `forward_folder` (default `_reversa_forward`)
   - `user_name`, `chat_language`, `doc_language`
   - `doc_level` (default `complete`)
2. Read `.reversa/config.toml` section `[specs]` to understand `granularity` (module / use-case / endpoint / hybrid / feature / custom).
3. Check prerequisites:
   - `_reversa_sdd/` must exist with at least one unit folder containing `requirements.md`.
   - If `_reversa_sdd/` is empty or absent, abort with a clear message pointing to `/reversa`.
4. Verify MkDocs availability:
   - Check if `mkdocs` is installed (`which mkdocs` or `pip list 2>/dev/null | grep mkdocs`).
   - If not installed, offer to install it:
     - `pip install mkdocs mkdocs-material mkdocs-pdf-export-plugin`
   - If installation fails (e.g., no Python/pip available), abort with installation instructions.

## Process

### Step 1: Scan and classify source files

Scan `_reversa_sdd/` recursively and classify all markdown files into categories:

| Category | Pattern | Purpose |
|----------|---------|---------|
| **Global overview** | `_reversa_sdd/architecture.md`, `domain.md`, `code-analysis.md`, `inventory.md`, `dependencies.md`, `gaps.md`, `confidence-report.md` | High-level system documentation |
| **Architecture (C4)** | `_reversa_sdd/c4-*.md`, `erd-complete.md` | Architecture diagrams in Mermaid |
| **Unit specs** | `_reversa_sdd/<unit>/requirements.md` | Core spec per module/feature |
| **Unit design** | `_reversa_sdd/<unit>/design.md` | Design details per module/feature |
| **Unit tasks** | `_reversa_sdd/<unit>/tasks.md` | Implementation tasks per module/feature |
| **Unit optionals** | `_reversa_sdd/<unit>/contracts.md`, `flows.md`, `edge-cases.md`, `decisions.md`, `questions.md`, `legacy-mapping.md` | Optional detail per module/feature |
| **Flowcharts** | `_reversa_sdd/flowcharts/*.md` | Process flow diagrams |
| **State machines** | `_reversa_sdd/state-machines.md` | State machine diagrams |
| **Permissions** | `_reversa_sdd/permissions.md` | RBAC / permission matrix |
| **ADRs** | `_reversa_sdd/adrs/*.md` | Architecture Decision Records |
| **Database** | `_reversa_sdd/database/*.md` | Database documentation |
| **Design system** | `_reversa_sdd/design-system/*.md` | Design tokens |
| **UI / screens** | `_reversa_sdd/ui/*.md`, `_reversa_sdd/*/screens.md` | Interface documentation |
| **Traceability** | `_reversa_sdd/traceability/*.md` | Traceability matrices |
| **Migration** | `_reversa_sdd/migration/*.md` | Migration artifacts |
| **Forward features** | `_reversa_forward/*/*.md` | Active forward features |
| **Greenfield** | `_reversa_sdd/ideation.md`, `personas.md`, `prd.md` | New project artifacts |
| **SDD specs** | `_reversa_sdd/sdd/*.md` | SDD component specs |

If `doc_level` is `essential`, only include core files (global overview, unit requirements + design, architecture, domain). Skip deep artifacts like ADRs, flowcharts, edge-cases.

If `doc_level` is `complete` or `detailed`, include all discovered files.

### Step 2: Build nav structure

Using the scanned files, build a hierarchical `nav` structure for `mkdocs.yml`. The nav mirrors the system's architecture:

```yaml
nav:
  - Home: index.md
  - System Overview:
    - Architecture: architecture.md
    - Domain Model: domain.md
    - Code Analysis: code-analysis.md
    - Inventory: inventory.md
    - Dependencies: dependencies.md
  - Architecture (C4):
    - Context: c4-context.md
    - Containers: c4-containers.md
    - Components: c4-components.md
    - ERD: erd-complete.md
  - Modules:                          # Only if granularity is module/feature/hybrid
    - Module A:
      - Requirements: module-a/requirements.md
      - Design: module-a/design.md
      - Tasks: module-a/tasks.md
      - Contracts: module-a/contracts.md
      - Flows: module-a/flows.md
    - Module B:
      - Requirements: module-b/requirements.md
      - ...
  - State Machines: state-machines.md
  - Permissions: permissions.md
  - Architecture Decisions (ADRs):
    - "001 - Title": adrs/001-title.md
    - "002 - Title": adrs/002-title.md
  - Database:
    - ERD: database/erd.md
    - Data Dictionary: database/data-dictionary.md
  - Traceability:
    - Code-Spec Matrix: traceability/code-spec-matrix.md
    - Spec Impact Matrix: traceability/spec-impact-matrix.md
  - Gaps & Risks:
    - Gaps: gaps.md
    - Confidence Report: confidence-report.md
```

**Key rules for nav construction**:
- Group related files under logical section headings
- Use the `granularity` from `config.toml` to determine how to organize unit specs:
  - `module`: group by module folder name, show requirements/design/tasks per module
  - `feature`: group by feature folder name
  - `use-case`: group by use case
  - `endpoint`: group by endpoint
  - `hybrid`: module at top level, nested use cases within
  - `custom`: follow user-defined folders
- Always respect existing file paths relative to `_reversa_sdd/`
- If traceability and gaps exist, place them in a dedicated section
- If `_reversa_forward/` has features, add a "Forward Features" section at the end

### Step 3: Generate index.md

Create an `index.md` that serves as the documentation entry point. Read `.reversa/soul.md` if it exists for the project description; otherwise, read `_reversa_sdd/architecture.md` for a summary.

The index must include:
- Project name and purpose
- Quick navigation links to key sections
- A summary table of what this documentation covers
- Document generation metadata (generated by Reversa, date, doc_level)

Template (use `doc_language` from state.json):

```markdown
# <Project Name> — Documentation

> Generated by Reversa on <YYYY-MM-DD>
> Document level: <essential | complete | detailed>

## Overview

<Short system description from architecture.md or soul.md>

## What's covered

| Section | Description |
|---------|-------------|
| [System Overview](architecture.md) | Architecture, domain model, code analysis |
| [Modules](<first-module>/requirements.md) | Per-module specifications |
| [Database](database/erd.md) | Data model and relationships |
| [Architecture Decisions](adrs/) | Key technical decisions |
| [Gaps & Risks](gaps.md) | Known gaps and confidence report |

## How to use this documentation

- The **nav sidebar** organizes content by architectural layer
- Use the **search bar** to find specific requirements or terms
- Use **PDF export** for offline reading (see toolbar)
- Each spec item is marked with confidence: 🟢 CONFIRMED / 🟡 INFERRED / 🔴 GAP
```

### Step 4: Generate mkdocs.yml

Generate a complete `mkdocs.yml` **at the project root** (alongside `_reversa_sdd/` and `.reversa/`). Use the template in `references/mkdocs-template.yml` and:

1. Replace placeholders with actual values from state.json
2. Inject the nav structure from Step 2
3. Configure the mkdocs-material theme with Reversa-branded colors
4. Enable Mermaid diagram rendering (critical for C4/ERD/flowcharts)
5. Enable PDF export plugin
6. Configure language based on `doc_language`

Since `docs_dir: .` (project root), the project structure becomes:

```
project-root/
├── mkdocs.yml                 # Generated here (at root)
├── docs/
│   └── index.md               # Entry page
├── _reversa_sdd/              # All spec content
│   ├── architecture.md        # Referenced as _reversa_sdd/architecture.md
│   ├── auth/requirements.md   # Referenced as _reversa_sdd/auth/requirements.md
│   └── ...
├── .reversa/
│   ├── state.json
│   └── documentation/
│       └── site/              # Build output (set by site_dir)
```

**Important**: Inform the user that `mkdocs.yml` is being created at the project root. If a `mkdocs.yml` already exists, offer to merge or backup.

All nav paths in `mkdocs.yml` must use `_reversa_sdd/` as prefix, e.g.:
```yaml
nav:
  - Home: docs/index.md
  - Architecture: _reversa_sdd/architecture.md
  - Auth/Requirements: _reversa_sdd/auth/requirements.md
```

This avoids any `docs_dir` path math issues. `site_dir` is set to `.reversa/documentation/site` to keep build output inside `.reversa/`.

### Step 5: Configure PDF export

Add PDF export configuration to `mkdocs.yml`. **Note**: `combined_output_path` is resolved relative to `site_dir`, so `../reversa-documentation.pdf` placed in `.reversa/documentation/site/` will output to `.reversa/documentation/reversa-documentation.pdf` at the project root.

```yaml
plugins:
  - search
  - pdf-export:
      verbose: true
      media_type: print
      enabled_if_env: ENABLE_PDF_EXPORT
      combined: true
      combined_output_path: "../reversa-documentation.pdf"
```

Explain to the user that PDF generation requires:
1. `mkdocs-pdf-export-plugin` installed (offer to install with pip)
2. A browser-based renderer (weasyprint or headless Chrome)
3. Running with `ENABLE_PDF_EXPORT=true mkdocs build`

Optionally, if `weasyprint` is available, use `mkdocs-with-pdf` plugin as an alternative that produces better results for large documents.

### Step 6: Build the site

After generating all configuration files:

1. At the **project root** (where `mkdocs.yml` is), run:
   - `mkdocs build` (generates HTML in `.reversa/documentation/site/`)
   - For PDF: `ENABLE_PDF_EXPORT=true mkdocs build`
2. Report the output paths:
   - HTML: `.reversa/documentation/site/index.html`
   - PDF: `.reversa/documentation/reversa-documentation.pdf`

If `mkdocs build` fails:
- Capture the error output
- Present the error to the user with common fixes:
  - Missing plugin: `pip install mkdocs-pdf-export-plugin`
  - Syntax error in YAML: check the generated `mkdocs.yml`
  - File not found: verify the nav paths match actual files
- Offer to fix and retry

### Step 7: Serve (optional development mode)

If the user wants to preview before finalizing:
1. Run `mkdocs serve` at the project root
2. Provide the local URL (typically `http://127.0.0.1:8000/`)
3. Tell the user to press Ctrl+C to stop the server

## Output

**Always:**
- `mkdocs.yml` — MkDocs configuration (at project root)
- `docs/index.md` — Documentation entry page
- `.reversa/documentation/site/index.html` — Built HTML site (after `mkdocs build`)

**If PDF export is enabled:**
- `.reversa/documentation/reversa-documentation.pdf` — Combined PDF

**If build fails:**
- `.reversa/documentation/mkdocs-build.log` — Build error log for debugging

**Cleanup note:** After the build, add `site_dir` (`.reversa/documentation/site/`) to the project's `.gitignore` if it's not already there.

## Non-destructive directive

Never modify files inside `_reversa_sdd/`. Only write to `.reversa/documentation/mkdocs/` and `.reversa/documentation/site/`. If these directories already exist from a previous run, offer to regenerate:

> "A previous MkDocs site exists. Do you want to:
> 1. Regenerate everything (overwrites mkdocs.yml and site/)
> 2. Only rebuild the site from existing config (preserves custom edits to mkdocs.yml)
> 3. Cancel"

Default to option 2 if `mkdocs.yml` already exists and the user is re-running.
