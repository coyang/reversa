# reversa-spec-sdd, Spec-Driven Development in Reversa

This skill conducts the complete SDD process within the Code New Project Agents pipeline: **decompose → draft → evaluate → iterate** until each spec is ready for the forward cycle.

The skill is a vendored version of the global `sdd-spec`, adapted for the Reversa context: reads `prd.md` as the primary source, writes to `_reversa_sdd/sdd/`, marks everything with the 🟡 seal, and ends with handoff to `/reversa-forward`.

## Why SDD?

Specs written before code save time because:

- They make ambiguities visible before they become bugs
- They align expectations between those who request and those who implement
- They serve as a permanent reference for testing, reviews, and onboarding
- They allow LLMs to implement with much more precision

The methodology here is **Pragmatic RFC plus LLM-First**: structured like an RFC (Problem / Goals / Design / Edge Cases), but optimized to be consumed by humans and AI agents.


## Autopilot awareness

This skill MAY emit `Type CONTINUE` style prompts between artifacts. Before doing so, read the `autopilot` field from `.reversa/state.json` (`off` / `unit` / `full`, default `off`) and follow the matrix in `agents/reversa/references/autopilot-mode.md`:

- `off`  → pause as usual between every file and every agent handoff.
- `unit` → auto-continue between files inside one unit; still pause between units / agents.
- `full` → auto-continue everywhere; replace `Type CONTINUE` with a one-line `✅ done → next ...` progress note. Do NOT prompt for confirmation.

Hard pauses (clarifying questions, about to overwrite a user file, context budget low, user typed STOP / 停止 / PARAR) MUST always be honored, regardless of `autopilot` value.

The user can switch mode mid-run by editing `.reversa/state.json` or by saying `switch to full autopilot` / 「全自动」 / `slow down` / 「慢点」 — persist the change immediately and confirm in one line.

Each generated spec goes to:

```
<output_folder>/sdd/<component-kebab-case>.md
```

For example: `_reversa_sdd/sdd/user-authentication.md`, `_reversa_sdd/sdd/payment-checkout.md`.

The component is decomposed from `prd.md` in the first phase.

## Mandatory 🟡 seal

All items in specs generated by `reversa-spec-sdd` must use the **🟡 PLANNED** seal (variant of 🟡 INFERRED used in other Reversa contexts). The 🟢 CONFIRMED seal is reserved for facts extracted from existing code by the Discovery Team, a rule inherited to avoid confusion between "legacy fact" and "forward hypothesis".

Each requirement, behavior, edge case, and acceptance criterion in the specs must start with 🟡.

## Workflow

### Phase 0, Component decomposition

Read `<output_folder>/prd.md` in full. From the "Scope", "Target personas", and "Acceptance criteria" sections, propose a decomposition of the product into logical components. Each component should represent a cohesive unit that will become an individual SDD spec.

Present the decomposition to the user:

> "From the PRD, I identified these logical components:
>
>   1. **<component 1>**: <one-sentence description>
>   2. **<component 2>**: <one-sentence description>
>   3. **<component N>**: ...
>
> Do you agree with this decomposition? Want to add, remove, or rename any?"

Wait for response. Iterate until confirmation (maximum 2 adjustments). For each confirmed component, normalize the name to kebab-case ASCII.

### Phase 1, Per-component interview (optional)

For each component, decide if the information in `prd.md` is sufficient:

- **Sufficient:** go directly to Phase 2.
- **Missing:** ask at most 3 focused questions, covering the points below that are absent:
  1. **The specific problem of that component:** "What is the role of `<component>` in the product?"
  2. **Success:** "How will you know this component worked? What can the user do?"
  3. **Scope:** "What is explicitly OUT of scope for this component?"
  4. **Edge cases:** "Can you already anticipate difficult cases or error situations in this component?"

Total limit: 3 questions per component, choosing the most critical ones.

### Phase 2, Draft the spec

Use the template in `references/spec_template.md` as base. Fill **all** sections:

- **Functional requirements:** format `RF-01`, `RF-02`. Each independently testable. Mandatory 🟡 seal.
- **Behaviors:** describe what happens, not how to implement. The spec defines the **what**, not the **how**.
- **Zero ambiguity:** if unsure, mark with `⚠️ OPEN:` and add to the Open Questions list.
- **LLM-readiness:** write as if a developer or LLM will implement without asking any questions.
- **🟡 seal on all spec items**, including RFs, edge cases, criteria.

Use `<doc_language>` for spec content.

### Phase 3, Automatic quality evaluation

After drafting each spec, run the scorer.

**Python detection:** try `python --version` or `python3 --version` via shell.

- **If Python available:**

  ```
  python scripts/spec_scorer.py --spec <output_folder>/sdd/<component>.md
  ```

  Use the script's literal output.

- **If Python not available (manual mode):** apply the procedure from the "Scoring on engines without Python" section below.

Scoring returns:

- **Total score** (0 to 100) with breakdown by dimension
- **Critical gaps** that need resolution
- **Suggestions** ordered by impact

Evaluated dimensions (see `references/evaluation_rubric.md` for details):

| Dimension | Weight | What it evaluates |
|---|---|---|
| Completeness | 30% | All sections filled, requirements covered |
| Testability | 25% | Verifiable requirements, clear acceptance criteria |
| Clarity | 20% | Absence of ambiguities, precise language |
| Scope | 15% | Non-goals defined, clear boundaries |
| Edge Cases | 10% | Error cases and system limits covered |

### Phase 4, Iteration

Based on the score:

1. Score **>= 80**: spec ready. Persist and move to next component.
2. Score **60 to 79**: fix obvious gaps automatically, then confirm with the user if anything critical is missing. Redo scoring.
3. Score **< 60**: go back to Phase 1 with questions focused on the gaps. Redo scoring.

Limit: **3 iterations per component**. After 3 attempts, persist with the current score and add a `## Quality pending items` section to the file.

At each iteration, show the delta: "went from 54 to 71, 2 critical gaps remain".

### Phase 5, Persistence and handoff

For each completed component:

1. Write `<output_folder>/sdd/<component-kebab-case>.md` with atomic write (tempfile plus rename), UTF-8 without BOM.
2. Include the **evaluation report** at the end of the file (score + gaps + suggestions).
3. If the file already exists, ask the user if they want to overwrite.

After generating **all** specs, display the consolidated report:

> "`<user_name>`, SDD generation complete. Specs created in `<output_folder>/sdd/`:
>
> | Component | Path | Score | Iterations |
> |---|---|---|---|
> | <comp1> | <output_folder>/sdd/<comp1>.md | 87 | 1 |
> | <comp2> | <output_folder>/sdd/<comp2>.md | 73 | 2 |
> | <comp3> | <output_folder>/sdd/<comp3>.md | 68 | 3 (with pending items) |
>
> All items marked with 🟡 seal (planned).
>
> Next step: run `/reversa-forward`, which will consume these specs and start the evolution cycle toward code.
>
> Type **CONTINUE** (or **继续**) to start `/reversa-forward`, or pause here."

Never proceed automatically.

## Scoring on engines without Python

When `python --version` and `python3 --version` fail, activate manual mode:

1. **Read `references/evaluation_rubric.md`** for the criteria of each dimension.
2. For each of the 5 dimensions, mentally evaluate the spec and assign a score from 0 to 100, justifying in 1 to 2 sentences:

   - **Completeness (30%):** are all 9 mandatory sections filled? Do RFs cover the declared scope?
   - **Testability (25%):** are RFs independently verifiable? Do acceptance criteria have Given/When/Then format or equivalent?
   - **Clarity (20%):** are there vague phrases (intuitive, fast, easy)? Are there contradictions?
   - **Scope (15%):** are non-goals explicitly declared? Clear boundaries?
   - **Edge cases (10%):** are at least 3 error/limit cases covered?

3. **Calculate the weighted score:**

   ```
   score = (Completeness * 0.30) + (Testability * 0.25) + (Clarity * 0.20)
         + (Scope * 0.15) + (Edge Cases * 0.10)
   ```

4. **List gaps** in order of criticality (blockers, important, improvements).

5. **Render the output** in the same format as the script:

   ```
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   TOTAL SCORE: <NN>/100
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   Breakdown:
     Completeness:    <NN>/100 (weight 30%)
     Testability:     <NN>/100 (weight 25%)
     Clarity:         <NN>/100 (weight 20%)
     Scope:           <NN>/100 (weight 15%)
     Edge Cases:      <NN>/100 (weight 10%)

   Critical gaps:
     - <gap 1>
     - <gap 2>

   Suggestions (by impact):
     1. <suggestion>
     2. <suggestion>
   ```

The result in manual mode should be equivalent to the script for the same spec.

## Signs of a bad spec (avoid)

- Requirements that cannot be tested ("the system must be intuitive")
- Scope section absent or vague ("we'll see what makes sense")
- Mixing technical implementation design with expected behavior
- Contradictory requirements not flagged
- No acceptance criteria defined
- Error edge cases completely absent

## Signs of a good spec (aim for)

- Any developer can implement without asking questions
- Any QA can write tests from it
- Non-goals are as clear as goals
- Error cases have defined behavior
- Each requirement has a unique traceable ID
