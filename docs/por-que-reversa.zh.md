# Reversa 为什么存在

## 经典问题

想象一个 2015 年上线的系统。当初写它的人没有一个还留在公司。原始的文档是一个 Word 文件，没人知道丢到哪里去了。代码能正常运行，每天都在产生收入，但有些部分没人敢碰，因为"动这里，那里就会出问题"。

那个系统承载了多年积累的知识：隐式的业务规则、在截止日期前深夜 11 点做出的架构决策、埋藏在类似 `process_v2_final_revised` 这种名称的函数中的关键逻辑。知识是存在的。它在代码里。但它被困在其中，任何 AI agent 都无法访问。

---

## AI agent 的问题

AI agent 在创建和演进软件方面具有变革性。但它们依赖于规格说明才能安全地运行。

对于新系统，这种方法很有效：你写 spec，agent 执行。但对于遗留系统呢？agent 无从知道哪些是不能破坏的。如果你让它"重构支付模块"，它会根据代码*看起来*做的事情来重构，而不知道代码*本应*做什么。

结果是那种经典时刻：agent 破坏了一条没人记录过的业务规则，你只有在客户打电话投诉时才发现。

---

## 解决方案

Reversa 是遗留系统和 AI agent 之间的桥梁。

它分析现有代码并提取积累的知识：业务规则、流程、模块之间的契约、回溯式的架构决策。然后将一切转化为可执行、可追溯的规格说明，任何编码 agent 都能直接使用。

产生的结果不是供人闲暇时阅读的文档，而是**可执行的操作契约**，允许 agent 忠实地按照已有的系统来演进它。

---

## 目标用户

- **拥有遗留系统的公司**，希望在不重写一切的前提下进行现代化
- **使用 vibe coding 的团队**，从未写过正式的 spec（不做评判）
- **接手项目的开发者**，需要在修改任何东西之前了解系统做了什么
- **任何**拥有可运行但没有文档的系统、想要安全地使用 AI agent 来演进它的人

---

## Reversa 不是什么

Reversa 不是传统的静态分析工具。它不生成代码覆盖率，不做 linting，不标记 bug。它是一个**知识提取**框架：它将代码中隐式存在的东西变成形式化规格说明中显式的内容。

它也不是魔法解决方案。系统中有一些部分确实是静态分析无法触及的（依赖真实数据的行为、只存在于某人大脑中的规则），这些将显示为空白，标记为 🔴，等待人工验证。诚实是设计的一部分。
