# 范式转变

大多数迁移在表面之下就已经失败了。用户以为他们只是在更换语言（PHP → Node、Java → Go），但实际上他们在更换范式。而范式塑造的远不止语法：它塑造了你对并发、一致性、执行顺序、错误处理的思考方式。

Paradigm Advisor 的存在就是为了在架构被画出之前，强制启动这场对话。

---

## 为什么这很重要

考虑一个简单的遗留系统规则：

> "当订单确认后，扣减库存并发送邮件。如果任何步骤失败，回滚所有操作。"

在同步过程式的 PHP 中，这是一个带有 `BEGIN / COMMIT / ROLLBACK` 的数据库事务。它之所以能工作，是因为所有东西都在同一个进程中、同一个 HTTP 请求中运行。

在无服务器事件驱动的 Node 中，**没有任何事务能跨越多个 handler**。每个步骤是一个函数，每个函数是一个事件，而邮件发送失败发生在库存已经被扣减*之后*。你需要 saga、幂等性、重试、死信队列。这不是 bug。这是范式的本质。

将该规则"原样"迁移到 Node 会出问题。但一个通用的 LLM 会原样迁移它，因为遗留 spec 里就是这么写的。

Paradigm Advisor 能在早期就发现这个问题。

---

## 它做什么

1. **检测** `_reversa_sdd/` 中 spec 所反映的遗留系统范式。寻找具体的标记：类结构、数据访问模式、事件的存在、线性同步流等。

2. **推断** brief 中声明的目标技术栈的自然范式。现代 Node 是异步/事件驱动的。Go 是 CSP/goroutine 的。Elixir 是 Actor 模型的。没有"中立"的选择。

3. **识别差距**，使用遗留系统本身的具体示例，而非抽象描述。

4. **向用户呈现 3 个选项**：
    - **采用技术栈的自然范式**（变革型）。按照新模型重写规则。工作量更大，但更协调。
    - **强制采用与遗留系统相似的范式**（保守型）。尝试在异步技术栈上保持同步模型。工作量较小，但更脆弱。
    - **混合型**（平衡型）。部分规则遵循新范式，其他规则保持旧范式。按类别决策。

5. **记录** 决策到 `paradigm_decision.md`，以及**推导出的 appetite**（`conservative` / `balanced` / `transformational`），这将影响所有后续 agent。

---

## 它不负责什么

- 替你决策。它提供教育、呈现选项并强制做出选择。决策权在人。
- 更改目标技术栈。如果 brief 说用 Node，它就用 Node。更改技术栈意味着重做 brief。
- 在没有证据的情况下检测范式。关于遗留范式的每一项声明都带有可追溯的证据（使用 🟢🟡🔴⚠️ 标记）。

---

## 示例：过程式 PHP → 异步 Node

| 方面 | 过程式 PHP | 异步/事件驱动 Node |
|---|---|---|
| 并发 | 每请求一个进程，天然的锁机制 | 隐式并发，需要手动加锁 |
| 事务 | `BEGIN/COMMIT` 在数据库中跨越整个请求 | Saga 或 Outbox，没有分布式事务 |
| 错误 | 抛出异常并任其崩溃，或显式回滚 | 重试、死信队列、幂等性 |
| 顺序 | 控制器中的线性流程 | 事件可能乱序到达 |
| 状态 | 服务端 Session | 无状态，状态放在 token 或外部存储中 |

如果迁移忽略了这些问题，新系统在测试中"能用"，但在真实负载下的生产环境中会崩溃。Paradigm Advisor 在 Designer 开始之前就能发现这些问题。
